- 実装の変更: 不要
- 承認日:

- 起こした役: Spec Steward

## なぜ変えるか

houki-hub #27 で、ツールごとに「どう処理されるか」を人が読むページを作る。今の `spec.md` は「できること」を仕様 ID ごとに並べているだけで、どの順に確かめ、どこで分かれてどのエラーになるかは、各節の本文を読み合わせないと分からない。この順序と分岐を 1 枚の図にして、`spec.md` に置く。

## 変わる振る舞い

無い。出荷済みの振る舞いを図に書き直すだけで、実装もテストも変えない。

## 何を変えるか

各 `spec.md` の `## 入力` の後に、次の形の `## 処理の流れ` の節を足す。

- 1 行目に説明文（「呼び出しを受けてから応答を返すまでに、何をどの順で確かめるかを示します。図の中の番号は「できること」の仕様 ID の末尾 3 桁です。」）
- Mermaid の `flowchart TD` 1 つ。各ノードに、そのノードに当たる仕様 ID の末尾 3 桁を（001）の形で書く
- 描くのは「できること」に仕様 ID のある振る舞いだけ。「未決」と「できないこと」は描かない。流れが途切れる箇所（合う文書があるときの応答の形が未決のもの）は、番号を付けずに「（応答の形は「未決」の N）」と書く
- 関数名・テーブル名は書かない（`spec.md` の方針のとおり）

14 ツールとも、「できること」の仕様 ID はすべて図のどこかに出ている。図は Mermaid の描画（mermaid-cli 11）で構文が通ることを確かめた。

## 変わらない振る舞い

- 仕様 ID、「できること」「できないこと」「未決」の本文
- `spec-ids check` の結果（ID を数えるのは見出しだけで、図の中の番号は数えない）

## 対象外

- 「目的」の節（置かない。ツールが何をするかは 1 行目とアクター、使う場面は houki-hub #6 のユースケースページに書く）
- AGENTS.md への書式の追記（仕様 PR では AGENTS.md を変えないため、別の PR にする）
